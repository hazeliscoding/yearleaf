# Roadmap

Derived from the accepted architecture record
([docs/Infinite-Desk-Calendar-Architecture-Decisions.md](docs/Infinite-Desk-Calendar-Architecture-Decisions.md)),
whose delivery order this tracks. Checked items are done; the rest are in
planned order. Version 1 is a fully offline, single-user desktop
application — no accounts, no cloud, no sync.

Review-gate and persona findings that do not change what the application can
represent live in the [Polish backlog](#polish-backlog-standing) at the end,
which Milestone 6 draws from. Split applied 2026-09-19.

## Milestone 3 — Desktop shell and persistence (delivery steps 1 & 5)

- [x] Tauri 2 shell: window management, capability ACL, dev/build wiring (native dialogs land with the features that need them; packaging moved to milestone 6)
- [x] SQLite behind narrow Tauri commands (WAL enabled): rusqlite + rusqlite_migration ([design record](docs/design-sqlite-persistence.md)) — no SQL crosses IPC
- [x] Schema foundation: versioned migration machinery plus `desk` and `calendar_object` (migration 1). Decided 2026-09-17 — schema v1 grows one migration per feature rather than landing all seven tables up front, so each table is designed alongside the flow that uses it
- [x] Reopen the last desk on launch (single `default` desk for now); crash-safe flushing — one transaction per committed command, WAL replay on reopen
- [x] `SQLitePersistence` implementing the `@infinite-desk/persistence` contracts, injected only under Tauri (in-memory fallback in the browser)
- [x] The claim the product rests on is executed rather than argued. Every other persistence test reopened a connection inside one process, and the Playwright suite runs the browser build against in-memory persistence by configuration, so "your desk is still there tomorrow" had never been run. `src-tauri/tests/restart.rs` spawns separate operating-system processes: one saves an object through the real IPC boundary and is then killed outright with `abort`, so nothing is unwound and no connection is closed; a fresh process opens the same files and reads it back. The object is compared field by field — fractional position, negative rotation, nested checklist payload — not counted. WAL replay is measured rather than assumed: the database file is copied away from its log and the desk is gone, which is what proves the commit was being recovered from the log in the first place. Four limits, all stated in the file, and one claim deliberately not made — a surviving log does not establish that nothing was checkpointed, since SQLite may checkpoint during a commit, so the orphan comparison carries that weight rather than the log's existence. It drives the same commands the webview invokes with the same wire shapes, but the Angular adapter that calls them is not in the loop, so this proves what the persistence layer is asked to store survives, not that the app asks for the right thing. The process is killed *after* a successful save, so a write in flight or an edit the app had not yet sent is outside it. It covers one sticky object, not events or attachments, and bypasses the real startup path. And `synchronous=NORMAL` leaves the log to the operating system's cache between checkpoints, so this is survival of a dead *process*, not of a power cut
- [ ] The restart proof's child processes have no timeout: `Command::output()` waits as long as they take, so a child that hangs hangs the suite instead of failing it. Adding one means spawning the wait on a thread and killing by process id when it expires, whose only real difficulty is draining the child's output while polling so a full pipe cannot deadlock the wait — `Child::try_wait` and `kill` are portable. Worth doing when these run unattended, which is the same moment the item below becomes urgent. Raised by Thorn on 2026-09-18
- [x] Every suite now runs, and something other than memory runs them. `pnpm test` gained the Rust suite — packages, desktop unit, cargo — and stays a fast default at 15s warm, because cargo adds about two seconds once the crate is built. `pnpm test:all` adds Playwright for 2m51s total, which is the CI command. A single GitHub Actions workflow on push and pull request runs `test:all`, so what CI means and what a terminal means cannot drift. `reuseExistingServer` is off: a server left from an earlier run keeps serving the bundle it started with, which cost a false pass and three killed servers in one afternoon, and refusing to reuse turns that into a loud "port already in use" at no cost in the ordinary case, where there is nothing to reuse
- [x] The mock-runtime tests had only ever been run on Windows, and nobody could have known. `InvokeRequest` hardcoded `http://tauri.localhost`, which is the shim Tauri serves from on Windows and Android only; everywhere else it is `tauri://localhost`, and the capability matches on `URL: local`. So on Linux the ACL refused every request and four of five IPC tests plus three of four restart tests failed — a platform-shaped break that no amount of running them locally would ever have surfaced. Both files now choose the URL the way Tauri does. Found by running the suite in a Linux container before trusting it to CI, which is the only reason it was caught before the first red build rather than after it

## Milestone 4 — Objects and input depth (delivery steps 6–7)

What changes the object model lives here. Review and persona findings about
finish and affordance live in the Polish backlog.

- [ ] Task objects in day cells. This line used to claim there was no way to create a checklist sticky and that the Task tool armed inertly — both struck 2026-09-19, disproved by the suite by name: `creation.spec.ts` "the task tool creates a checklist sticky with a tickable item" (presses `k`, clicks, and a checklist exists), and the placement fix is the [x] below. Checklist toggling and editing hold too: `workspace.spec.ts` "clicking a checkbox toggles the item and undo restores it" and "checklist stickies edit line-per-line and keep done state by position", and a Task-tool-created checklist re-edits by double-click (`workspace.spec.ts` "a checklist made with the Task tool re-edits by double-click" — the test the triage recorded as owed, paid 2026-09-19) (Marcus's contrary report is corrected on his Polish item — his real gap is that no *keyboard* route into editing exists). What actually remains of this line: the seed's in-cell tasks ("Pay electric bill", due dates, priorities) have no object type — the Task tool makes a desk sticky, not a day's task — so day-cell tasks are still to be designed and stored
- [x] A tick travels with its words, never with its row number. `setChecklistItems` copied done state across by position, so retyping the same items in a new order reassigned every tick — Marcus's 2026-09-18 corruption: ticks on rows 1 and 3 stayed on rows 1 and 3 through a reorder, and "my checklist now claims I've defended my prospectus", with undo recording the result as a legitimate edit. Each edited line now claims the first unclaimed old item with exactly the same label, so reorders and insertions carry ticks with their items, duplicates match in order (an unchanged list is unchanged), and a deleted line takes its tick with it. One trade-off made deliberately and stated in the code: rewording a done item unticks it, because the fallback that would preserve the tick — match by row when the words changed — is the same rule that hands a tick to a new line typed above a done one, and unticked-after-reword is visible and one click to repair where falsely-ticked is silent. The e2e that had asserted the old rule by name ("keep done state by position") is renamed; it only ever passed because it appends, the one edit where position and identity agree
- [x] A day cell draws only what the desk holds. Events became real rows, but the sample month's `tasks`, `range`, `hand` and `img` never did: `dayContentFor` merged them over every September 2026 cell, so a user's real September came back with handwriting, taped photos and a multi-day bar beside their own events — content no tool created, no gesture edited and no key deleted, and nothing on screen distinguished it from something they had written themselves. Every other month was bare, which is the same fiction seen from the other side. The merge is gone; `MONTH_CONTENT` stays as the seed it already was for events, with the rest kept as the demo desk it describes for when those object types are real enough to seed the same way. A first run still reads as lived-in — thirteen real events across the month, plus the stickies, checklist, picture, file and note beside it — so this needed no onboarding or empty state to replace it
- [ ] The demo desk is thinner than the design reference until tasks, ranges, handwriting and in-cell photos are real objects: the seed rows for all four are still in `sample-desk.ts` and are no longer drawn. Seeding them belongs with whichever feature lands first, the way the September events were seeded once they had somewhere real to live. Three things the 2026-09-18 gates measured while confirming the first run still reads as a desk. The floats east of the sheet carry 11.1× its chromatic density (28.42% against 2.57%), so the eye lands on the yellow sticky rather than the calendar — arguably right for a *desk*, but it was not chosen. Sep 1–6 now reads emptier than the out-of-month filler row beneath it (0.21% against 0.26%), which is the weakest possible first read at the corner the eye enters. Both would be fixed in kind by a couple more seeded events in the first week, deliberately not done here: pressing a demo desk for density is exactly how the fiction started, and whether the opening month should be dressed is a product call. Also unpriced: weekend columns and out-of-month cells take the identical fill (`month-view.ts:85`), 1.113:1 against weekday paper in light and 1.132:1 in dark, so only numeral colour separates a September Saturday from an October filler day — fine when cells were full, and now carrying more of the sheet's structure. And `MONTH_CONTENT` is still typed as the renderer's `DayContent`, which is the affordance that made handing it to the renderer the obvious thing to do: `event-store.ts` silently reads `events` and skips the other four, so a new `hand` entry would compile, change nothing and say nothing. A local seed type with the parked fields under their own key would make consumed and parked distinguishable
- [ ] The zoom ladder above the month tier has quietly collapsed to one rung, found independently by both 2026-09-18 gates. `showMeta` is the only cell-level difference between `month` and `week`/`day` (`month-view.ts:179`) and it gates on `event.meta` — but `EventRecord` has no `meta` field, and `sampleEventRecords` builds rows from id/title/timeLabel/colour/variant/date alone. So nothing has populated `meta` since events became real rows, and Day at 160%, Week at 78% and Month at 47% draw an identical composition at three scales. The same seeding gap costs the seeded month its repeat markers, though not the feature: setting Repeats in the inspector writes an `rrule`, `dayContentFor` maps that to `recurring: true` and the marker draws correctly. What is lost is the sample — Sep 8's "Client review" is marked `recurring: true` in the seed and comes back `recurring: false` from the desk, so the demo desk shows no series until the user makes one. Removing the tasks and handwriting did not cause this, it removed the last in-cell content that hid it. The renderer's header comment has been corrected to say the rungs are unreachable rather than to advertise them; giving `EventRecord` its metadata and its recurrence at seed time is what actually returns them
- [ ] Two latent defects in the renderer paths deliberately kept for milestone 4, neither reachable until those object types are real. A photo caption overflows its cell: the fit test at `month-view.ts:220` is `y + 70 <= bottom`, but the block draws a 66-tall rect at `y` *and* a 16px caption at `y + 68`, landing near `y + 87` — up to 17 world units past `bottom` and across the grid line. And a multi-day range never formed a continuous bar: `drawRangeBar` is called from the per-cell content stack, so its `y` depends on how many events precede it in that particular cell, which is why the Kyoto range used to render as three segments at three different heights. It needs a per-week-row baseline rather than a stack position

- [x] Fix: `Shift+T` (the palette's advertised Today shortcut) is swallowed by the Text tool binding; keystrokes landing before the editor takes focus no longer arm tools or start pans
- [x] Fix: `Ctrl+Y` doesn't redo on Windows — the only redo was `Ctrl/⌘+Shift+Z`, so the chord a Windows keyboard reaches for first fell through every branch and did nothing at all. `Ctrl+Y` is now accepted on every platform rather than gated on one: a Mac user will not press it, and a platform check here would be a second thing to keep in step with the hints. - [ ] Multi-select and the lasso: the lasso tool arms but does nothing, marquee-drag pans, Shift+click doesn't extend — promoted from the milestone-2 deferral by persona demand; duplicate/copy-paste of objects belongs with it
- [x] A way to reach next month. Arrows either side of the navigator label move what the label names — a month, or a year at the year tier — and PageUp/PageDown do the same without a pointer. Stepping keeps your zoom and your place within the month, and crosses the row and year wraps that scrolling cannot: months run three across, so dragging downward from September arrives at December, which a professional calendar reader mistook for the weekday columns being misaligned. The navigator now names the month filling the screen rather than the one under the centre point, which is how it came to report "July 2026" while October and November were on screen. - [x] The scroll trap is closed on the canvas, where the deceiving happens. A sheet whose own title has scrolled off the top keeps naming itself in a band pinned to the top of the viewport, with the weekday letters aligned to the columns they name — which is the other half of the misreading, since the reader who got lost concluded the columns themselves were wrong. The band names the sheet that is *unlabelled*, not the one filling the screen: drifting down from September puts September's last rows along the top and December's sheet, header and all, below them, and December above September is exactly the surprise. So the moment a drag crosses a quarter now announces itself. The band stays out of a whole-year view where every sheet is titled, off bare desk where there is nothing to name, and off a sliver of the month above that the default framing leaves showing over the gutter
- [x] The gutters are signposted. A seam states the distance it spans rather than naming the sheet across it — the count of bars *is* the distance, three across a horizontal gutter and one down a vertical one, undirected so neighbouring seams cannot contradict each other and the mark stays true read upward. `3 MONTHS` is set once along each seam, `1 MONTH` along each side gutter, and at a row's end a catchword names the month the sequence continues on, marked with a stroke that drops a row and runs back to the start of it. The reader who had been caught three times confirmed the distance label works — "someone finally put a sign on the trapdoor" — and would now scroll freely
- [x] Fits, jumps and steps glide instead of cutting. `ViewportStore.animate` had been written in five places and read nowhere, so nothing was animated despite the code documenting itself as animated. Two reviewers independently said the cut was the reason the layout stayed invisible: reaching October without ever learning it sits below July and two columns left. Zoom eases geometrically, a gesture abandons a flight in progress, the first framing on load does not fly in from the origin, and `prefers-reduced-motion` turns it off
- [x] Enter commits an event title and hands the keyboard back, which is what Tab, click-away and Escape already did. Every editor on the canvas is the same `textarea` — including the event title's one-line box — so Enter's default was to insert a newline the box is not tall enough to show, and focus stayed in a draft that then looked empty because the title had scrolled out of it. Behind `App.onKeyDown`'s `typing` guard that killed every navigation key: PageDown and `Shift+T` did nothing and the application read as frozen, with Enter the one exit that did not exit. The decision is recorded once, on the editor view-model that already discriminates the three editing modes, rather than in the keydown handler: a `singleLine` flag the template passes down, so a fourth editing mode cannot be added without answering the question — it is a compile error, the way deleting the `command` icon made `icon="command"` one. Committing blurs rather than calling `commitEditor`, so all four exits stay one commit path and none of them can drift. The key is compared rather than bound as Angular's `keydown.enter`, which ignores Shift+Enter and would have let a newline back into the one-line box by another route. Where lines are the content — text objects, and checklists that store one item per line — Enter is still a newline. Mid-composition the exit stands down: Enter belongs to the input method there, choosing a candidate, and committing on it stored the reading — かいぎ — and took the box away mid-word, so a title could not be typed in Japanese or Chinese at all. The old newline behaviour absorbed that harmlessly, which is what made it this exit's defect to introduce and this exit's to guard
- [x] A selection the inspector would hide is uncovered, and nothing else moves. Marcus read this as a ~264px opaque panel the canvas did not inset for; the opposite is true. The shell is `grid-template-columns:44px 1fr auto`, so selecting anything genuinely narrows the canvas cell, and `setViewSize` recorded the new size while re-framing only on the very first layout — so the world stayed pinned top-left and the strip the panel took stopped being reachable. That is how a note placed near the right edge vanished when its own selection opened the panel, and why the click aimed at it afterwards landed on the panel, with the typed words falling through to the canvas and arming a tool per letter. Fixing the item as written — padding for an overlay that is not one — would have moved nothing. `ViewportStore.revealHorizontally` now pans the least distance that brings a world rect inside the view and nothing at all when it is already there, called after a resize with the rect of whatever is selected (an event chip resolves to its day cell). Holding the world point under the viewport centre was built first and measured: it pays on every selection instead of the ones at risk, sliding the desk by half the lost width whether or not anything was covered, shearing the far column off the opposite edge, and at 132px it was still not enough to uncover the sticky that prompted this, which needed 170. Both edges cannot be kept when the view loses 264px; panning only on occlusion keeps them whenever nothing is at stake. The reveal is horizontal by construction, not by configuration: a grid column narrows the canvas and never shortens it, so a vertical correction is motion with no cause a reader can see — and it drove the rect under the pinned band, which is an opaque 39px the viewport knows nothing about, making the cell you had just selected the one whose date you could not read. It fires on selection as well as on resize, because choosing a second object while the panel is already open is not a resize, and that object is exactly as coverable as the first — which is the more common flow of the two, and was the whole original bug intact one selection later
